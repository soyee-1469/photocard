# 포토카드 작업 지침 (soyee-1469/photocard)

사내 메신저 토마톡에 들어갈 포토카드 서비스. 저장소는 공개(public)이고, GitHub Pages는 `gh-pages` 브랜치에서 서비스된다. 사용자와는 한국어 반말로 소통한다.

## 1. 절대 규칙
- 수정은 `service/` 폴더 안에서만 한다. 루트 Expo 앱, `flutter/`, `motion/`은 건드리지 않는다. (`motion/`은 PR #2 전용.)
- 새 이미지를 임의로 생성하지 않는다. 기존 에셋을 최대한 재사용한다. 카드 뒷면은 공용 `service/assets/fx/card_back.png`.
- 사용자의 최종 승인 전에는 머지하거나 배포(`main` 반영)하지 않는다. PR 미리보기 배포(`gh-pages`의 `service/pr-<번호>/`)는 괜찮다.
- 실제로 돌려 보거나 렌더해 보지 못한 작업은 완료라고 하지 않는다.

## 2. 작업 흐름
1. 요청을 GitHub Issue로 기록한다.
2. 구현 전에 계획을 먼저 쓰고 사용자 승인을 받는다. 판매처 조사처럼 근거가 필요한 부분은 조사 결과를 붙인다.
3. 승인 후 별도 브랜치에서 구현하고 PR을 연다. 의존 PR 위에 쌓을 때는 base 브랜치를 명시한다.
4. 커밋을 push하고 `git ls-remote`로 원격에 실제로 올라갔는지 확인한다.
5. `service/`의 `build-pages.sh <PR번호>`로 미리보기를 배포하고, 배포본 `version.json`의 SHA가 PR head와 같은지 확인한다.
6. 공개 미리보기 URL(https://soyee-1469.github.io/photocard/service/pr-<번호>/)로 e2e를 돌린다. `force: true` 클릭이나 URL 직접 이동으로 실제 클릭을 대체하지 않는다. 테스트를 줄였으면 이유를 적는다.
7. 실제 화면 스크린샷을 남긴다. 404나 빈 화면 스크린샷은 실패로 본다.
8. 검수 결과를 PR 댓글로 남긴다. 마커: `<!-- auto-review sha=<SHA> -->`, `<!-- auto-fix-round=N -->`. 요구사항(Issue)과 코드·화면을 대조한다.
9. 검수 후 Cursor 수정 에이전트를 자동으로 띄우지 않는다. 자잘한 수정은 사용자가 에디터에서 고치도록 정리하고, 큰 수정만 클라우드 에이전트로 보낼지 사용자에게 묻는다. 같은 문제가 두 번 안 고쳐지면 `needs-human` 라벨을 단다.
10. 결과를 사용자에게 미리보기 URL과 스크린샷과 함께 보고한다.

## 3. 사용량 절약 규칙 (Cursor)

### 3-1. 2026-09-28 작업에서 사용량이 많이 나간 곳
계정의 클라우드 에이전트 목록 기준. 작업별 사용량 숫자는 확인할 수 없어서 에이전트 개수와 반복 횟수로 판단한 것.
- **PR #7 자동 검수 에이전트 17개.** 커밋이 올라올 때마다 검수용 클라우드 에이전트를 새로 띄웠다. 하루 동안 photocard에서 띄운 에이전트 약 21개 중 17개가 검수용이었다. 새 에이전트는 매번 저장소를 처음부터 읽고, 설치하고, 테스트를 다시 돌린다. 클라우드 에이전트는 항상 Max 모드로 돌아서 한 번 한 번이 비싸다. **가장 큰 낭비.**
- **PR #7 수정 라운드 반복.** 같은 에이전트에 수정을 여러 번 보냈고, 매 라운드마다 배포, 전체 e2e, 스크린샷을 다시 돌렸다. 에이전트가 `force: true` 클릭으로 테스트를 우회하거나 테스트를 21개에서 10개로 줄여서, 다시 고치는 라운드가 더 생겼다.
- **PR #10 바인더 3라운드 연속 실패.** 2×2 배치가 세 번 모두 안 고쳐졌고, 매번 스크린샷 14장과 e2e 11개를 돌렸는데 스크린샷 대부분이 404였다. 화면을 보면서 한두 번 주고받으면 끝날 레이아웃 문제를 에이전트가 추측으로 반복했다.
- **작은 수정도 클라우드 에이전트로 보냄.** 닫기 버튼 위치, 공급 종료 아이콘 같은 파일 한두 개짜리 수정도 매번 테스트, 배포, 스크린샷까지 한 바퀴를 돌았다.

### 3-2. 최적화 규칙
1. **검수 에이전트를 띄우지 않는다. (2026-09-29 사용자 결정)** 검수는 Grok Bot이 직접 한다: PR diff 읽기, 헤드리스 Chrome으로 미리보기 렌더, 요구사항 대조. 작업 라운드가 끝났을 때 한 번만 하고, 이미 검수한 SHA는 건너뛴다. Cursor 검수 에이전트는 사용자가 명시적으로 요청할 때만 쓴다.
2. **자체 점검은 구현 에이전트 안에서 끝낸다.** 구현 지시문에 "push 확인, 배포, version.json SHA 확인, 공개 URL e2e, 실제 스크린샷"까지 넣어서, 검수하려고 새 에이전트를 띄울 일이 없게 한다.
3. **수정은 모아서 한 번에 보낸다.** 문제를 발견할 때마다 따로 보내지 말고, 검수 결과 전체를 한 번의 후속 지시로 보낸다.
4. **새 에이전트보다 기존 에이전트에 이어서 시킨다.** 새 에이전트는 저장소 파악부터 다시 한다.
5. **지시문을 구체적으로 쓴다.** 고칠 파일 경로, 컴포넌트 이름, 기대 화면(예: "바인더 한 페이지에 2열×2행, 카드 폭 = (화면폭-여백)/2")을 적어서 탐색과 추측을 줄인다.
6. **테스트와 스크린샷 범위를 줄인다.** 수정 라운드에서는 바뀐 화면의 e2e와 스크린샷만 돌린다. 전체 e2e와 전체 스크린샷은 마지막 라운드에 한 번.
7. **같은 문제가 두 번 연속 안 고쳐지면 멈춘다.** 세 번째 라운드를 돌리지 말고 사용자에게 넘기거나, 사용자가 에디터에서 화면을 보며 직접 고치게 한다.
8. **공통 지침은 저장소에 둔다.** 이 문서를 `.cursor/skills/`에 커밋해 두면 에이전트마다 긴 규칙을 지시문에 다시 붙일 필요가 없다.
9. **사용량이 떨어져 에이전트를 띄울 수 없으면** 반복 재시도하지 않고 한 번만 알린다.

### 3-3. 누가 하는 게 나은가
**사용자가 Cursor 에디터에서 직접 하는 게 훨씬 아끼는 일**
- 레이아웃, 간격, 문구, 버튼 위치, 아이콘 같은 자잘한 UI 수정. 화면을 보면서 바로 고치고 확인할 수 있고, 에디터의 로컬 에이전트는 Max 모드를 강제하지 않는다.
- 두 번 연속 안 고쳐진 시각적 버그(예: PR #10의 2×2 배치).
- 이미 받아 둔 로컬 저장소에서 스크립트 한 번 돌리기(`build-pages.sh <번호>`로 미리보기 재배포, e2e 한 번 실행 등).
- 이때 Grok Bot은 어디를 어떻게 고치면 되는지(파일, 원인, 기대 결과)를 정리해 넘기고, 끝난 뒤 미리보기를 확인한다.

**클라우드 에이전트에 맡기는 게 나은 일**
- 새 화면이나 여러 파일에 걸친 큰 기능(PR-B 구매·개봉·저장처럼). 오래 걸리고, 사용자가 자리를 비워도 진행된다.

**Grok Bot이 직접 하는 게 나은 일 (Cursor 에이전트 사용량 안 씀)**
- 계획 작성, 판매처 조사, Issue 정리, PR 댓글 작성.
- PR diff 읽기와 헤드리스 Chrome으로 미리보기 렌더 확인.

## 4. 소통 규칙
- 클라우드 에이전트를 띄우거나 이어서 시킬 때마다 바로 볼 수 있는 링크(https://cursor.com/agents/<id>)를 사용자에게 보낸다. "진행 중"이라고만 하지 않는다.
- 오래 걸리는 작업은 중간에 무엇을 끝냈고 무엇이 막혔는지 짧게 알린다.
- 사용자가 Cursor에 직접 작업을 시키는 동안에는 같은 브랜치에 에이전트를 띄우지 않는다.
